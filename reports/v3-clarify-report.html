2目的清单

每一条都能单独验收。"验收要点"是草稿，等你批准编码方案时一起锁定。

P1

语音识别更准

识别模型从 Whisper large-v3 换成 Qwen3-ASR-1.7B，普通话、会议场景、方言的错误率都明显下降。

验收要点：同一批中文录音，新引擎错字更少；Whisper 相关代码和模型管理全部移除
P2

边说边出字

按住快捷键说话时，屏幕上实时显示正在识别的文字（最后几个字可能还会修正）；松开后定稿。

验收要点：说话过程中字幕持续刷新（目标每 0.5–1 秒一次）；松开后得到完整定稿
P3

说完自动纠错

定稿后交给 qwen3.5:4b 只做纠错：改错别字和同音词、修专有名词、补标点、去口头禅，不改原意，然后输入到当前窗口。

验收要点：关键词表里的词能被纠正；原意和语序不变；润色可以关闭；失败时明确报错，不偷偷输入
P4

截图在原位置翻译，完全本地

框选截图 → 识别文字 → 在原位置显示译文；翻译由本地 qwen3.5:4b 完成，截图内容不出本机，断网也能用。

验收要点：断网可用；Google/百度/MyMemory 和百度密钥配置全部删除；译文显示在选区原位置
P5

全新界面

设置/管理页、状态栏 + 实时字幕、截图翻译浮窗、手机录音页四个界面用同一套设计重做，并且采用跨平台技术。

验收要点：四个界面与你选定的模板一致；现有功能逐项保留、替换或说明删除理由
P6

全平台结构 + API

识别、润色、翻译等能力全部做成本地服务 API，桌面界面、手机页、外部项目都只调 API；Linux 专用的快捷键、输入注入、截图部分隔离成平台层。

验收要点：每项能力都有 API 和文档；核心代码不依赖 Linux；以后加 Windows/macOS 只需新增平台层

3差异对比：现状 → 目标

现状部分来自源码，均带文件和行号；目标部分是已确定的逻辑，不涉及具体实现。

语音输入流程

现状 按住快捷键→ 录整段→ 松开→ 上传 wav→ Whisper large-v3→ 补句号→ 输入
目标 按住快捷键→ ★ 边录边推流→ ★ Qwen3-ASR 实时识别→ ★ 实时字幕→ 松开→ ★ 定稿→ ★ qwen3.5:4b 纠错→ 输入

现状依据：录音和上传在 daemon.py:1847-2035（VoiceRecorder），识别在 app.py:263-347，补句号在 daemon.py:1982 附近。

截图翻译流程

现状 框选→ tesseract 识别→ Google → 百度 → MyMemory（联网）→ 全失败则显示原文→ 整块盖在选区上
目标 框选→ ★ 识别文字（带位置）→ ★ qwen3.5:4b 本地翻译→ ★ 原位置显示（样式见 UI 模板）

现状依据：app.py:696-756（OCR 端点）、app.py:655（三引擎链）、app.py:741-751（失败返回原文）、daemon.py:1552（TranslationOverlay）。"识别文字用哪种 OCR"属于技术选型，编码前实测后决定。
另外发现一个现有问题：本机 tesseract 只装了 eng、chi_sim 语言包，而 app.py:714 请求 eng+chi_sim+jpn。实测结果是只打印 Failed loading language 'jpn' 警告、继续运行，所以日文目前识别不出来。

5代价与风险

标"预期"或"推断"的都还没有实测，编码前第一步就验证。

项内容依据编码前怎么处理
预期 显存两个模型合计约 9–11GB，显卡共 16GB（RTX 5070 Ti）模型体积估算，未实测实测
推断 实时刷新每 0.5–1 秒对已录音频重新识别一次，显卡要跟得上官方流式也是"分块重识别 + 允许回改"的原理实测每次重识别的耗时
待选 跨平台运行时候选：官方 qwen-asr（transformers，体积大）、transcribe.cpp（轻，但只到 v0.1）、sherpa-onnx（目前只有 0.6B）三个都只支持整段识别实测后选一个
推断 热词Qwen3-ASR 开源版文档里没有热词参数，关键词改由纠错模型处理官方 README 和示例里都没有这个参数查源码确认
预期 翻译质量完全取决于本地 4b 模型，长段专业文本可能不如在线翻译你已选择只用本地用真实截图试译
事实 桌面环境当前会话是 GNOME Wayland，守护进程靠 XWayland（GDK_BACKEND=x11）运行；实时字幕和原位浮窗要在 Wayland 下置顶、不抢焦点XDG_SESSION_TYPE=wayland，systemd/ollama-voice-daemon.service选桌面外壳时作为硬性条件
代价 工作量按全平台结构做，等于重写界面外壳并拆分两个大文件daemon.py 4539 行、app.py 1080 行拆成能分别验收的几个阶段
前置 未提交改动工作区里有大量未提交的快捷键改动（daemon.py +1949 行等），还有两个进行中的快捷键任务git status开工前先决定是提交还是收尾

6全新 UI

三套风格，每套都包含四个界面。直接用浏览器打开，顶部可以切换界面和状态，右侧标注了每个界面显示的数据和调用的接口。三套的设置窗口都是左侧菜单、右侧内容、浅色主题。选定的一套就是以后的 UI 验收标准，也可以按界面混搭，比如 A 的设置页配 C 的截图样式。

A · 极简 最简

中性浅色，一个青绿强调色。状态胶囊录音时向右展开成一到两行字幕；截图沿用"整块译文盖住选区"；设置页 8 个菜单，模型页只有两行。不需要后端提供新数据。

打开 A

B · 控制台 功能最全

桌面应用风格，可切换深色。左下胶囊带音量电平，底部居中大字幕，松开后高亮纠错改了哪些字；截图逐行盖在原文上（类似 Google Lens）；手机页带"上传→识别→润色→输入"进度。紫色"新增"标出的功能都需要你拍板，也都需要后端额外支持。

打开 B

C · 暖色延续 折中

沿用现在的暖纸色和青绿主色。胶囊上方叠一张浅色字幕卡（最多三行）；截图按段落原位覆盖，比整块更贴近原位置，又比逐行更不容易错位；手机页分"录音 / 历史"两个标签。

打开 C

选模板时要一起定的几点

待定"原位置翻译"是哪种：整块（A，现在的做法）、逐行（B）还是按段落（C）。逐行或按段落都需要识别接口返回每行或每段的位置；逐行时建议整段翻译后再分回各行，否则句子会被拆断
待定浮层是否也用浅色：A、B 的字幕和截图浮层是深色（盖在任何应用上都清楚），C 是浅色
待定B 的新增功能要哪些：音量电平、纠错高亮、桌面端历史"重发"、截图出错时的"打开设置"、快捷键冲突提示
待定手机端润色失败怎么办：模板默认和桌面一致，即显示原文、不输入，提供"发送原文"按钮；手机是否跟随同一个润色开关也要定
待定模型是否允许切换：按已定决策，模板里模型是固定的；以后打包给配置较低的电脑时，是否提供 Qwen3-ASR-0.6B 这样的轻量选项
已定实时字幕里"已稳定的字"和"还可能变的字"由后端划分，界面只负责显示，不自己猜
